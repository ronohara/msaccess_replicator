DAO type 101 — Attachment

Whether the three Python replicators carry the complex-type defect found in the Rust port. They carry the skip; they do not carry the defect.

Summary

Access stores an attachment in a field of DAO type 101. All three replicators — pg_replicator.py, my_replicator.py and ms_replicator.py — skip such a field when building a table's schema, and every one of them says so in its log. A separate investigation of the Rust port, msaccess-replicator-ng, found three things: the skip is silent there, it leaves the recordset's per-field type and scale metadata misaligned, and the row reader touches the attachment value on every row.

One sentence. The Python replicators share the first behaviour by design and announce it; the metadata misalignment and the per-row warning are properties of the Rust port's own implementation and cannot arise in the Python, which converts values without any per-field metadata at all.

The defect as found in the Rust port has three parts. This document answers each of them separately against the Python source:
  1. complex-type fields are dropped from the schema, silently;
  2. the recordset's per-field type and scale metadata is built from the filtered column list but indexed by DAO position, so every field after a dropped one is mis-scaled — silently, and only where the type is consulted (Currency and Decimal);
  3. the row reader asks every DAO field for its value, so it meets the attachment field and emits an unhandled variant type warning per row.

What the three replicators do

The skip, and the log that accompanies it

All three carry the same block, in the schema-building loop over the table's fields — pg_replicator.py:1777, my_replicator.py:1810, ms_replicator.py:1908:

# Skip complex field types (Attachment=101, MultiValue=102-109)
# These cannot be accessed as scalar values from a table-type recordset
if fld.Type >= 101:
    logger.info(f"  Skipping complex field '{decode_sketchy_utf16(fld.Name)}' (type {fld.Type}) in table {table_name}")
    continue

The column is then absent from table_info['columns'], so it is absent from the DDL, from the INSERT column list and from the update-set — exactly as in the port. What differs is the log line: it names the field and its type, and it is emitted at INFO.

That log line is always visible

This mattered enough to check rather than assume, because an INFO line that no handler accepts would be reporting in name only. In all three files the levels are set once at import and the run-time flags only ever lower the threshold:

logger.setLevel(logging.DEBUG)          # pg:31   my:31   ms:30
file_handler.setLevel(logging.DEBUG)    # pg:39   my:39   ms:38
console_handler.setLevel(logging.INFO)  # pg:48   my:48   ms:47

# and at run time (pg:4182-4193) — nothing ever raises the level above these
if args.debug:      logger.setLevel(logging.DEBUG); … StreamHandler → DEBUG
elif args.trace:    logger.setLevel(logging.INFO)
if args.verbose:    … StreamHandler → INFO

So the skip message reaches the console handler (INFO ≥ INFO) and the file handler (DEBUG ≥ INFO) in every mode, with or without --verbose, --debug or --trace. Nothing suppresses it.

The fallback when the table still will not open

If skipping the field is not enough and tdef.OpenRecordset() fails, all three handle it explicitly (pg_replicator.py:989-1003 and its counterparts):

except Exception as e:
    logger.error(f"Failed to open recordset for table {table_name}: {e}")
    logger.error(f"This may be caused by complex field types (Attachments, MultiValue) in the table.")
    logger.error(f"Skipping table {table_name}")
    print(f"ERROR: Cannot open recordset for {table_name} - table contains unsupported complex fields. Skipping.")
    self.validation_results[table_name] = { … 'error': str(e) }
    return

The table is skipped, printed to the console, and recorded as a validation failure with the underlying error — so the run ends with a report of what was left out rather than passing quietly.

What the port does that the Python does not

The metadata misalignment cannot arise here

The Rust defect exists because the port introduced two vectors — a per-field DAO type and a per-field decimal scale — built from the filtered column list and then indexed by DAO position. The Python has no such construct. Its copy loop iterates only the surviving columns and reads each value by its recorded position:

for col in table_info['columns']:                 # surviving columns only
    pos = col['field_position']                   # original position in tdef.Fields
    if pos >= recordset.Fields.Count:
        continue                                  # explicit bounds guard
    dao_val = recordset.Fields[pos].value
    py_val = convert_dao_value_to_python(dao_val)

And the conversion itself is driven entirely by the value (pg_replicator.py:99, my_replicator.py:99, ms_replicator.py:96) — it takes no column, no type and no scale: GUID unwrapping, date/datetime duck-typing, pass-through for Decimal, bool, int and float, and str() for anything else. With no positional metadata to shift, the shift the Rust port suffers has no expression in this code.

Why this matters beyond the one file. The Python field_position comment — "Original position in tdef.Fields for recordset indexing" — is the same design the port copied. The port faithfully reproduced the position mapping and then added a second, positional mechanism beside it; it is that addition, not the skip, that carries the risk.

The reader never touches the attachment

Because the Python iterates the surviving columns, it never asks the attachment field for a value — so there is no equivalent of the port's per-row WARNING: unhandled variant type. The Rust reader loops over every DAO field (0..field_count), meets the dispatch-valued attachment field, and reports it once per row. Reading fewer fields is also cheaper: the Python does not pay for a value it has already decided to drop.

Verdict, part by part

Part of the port's defect Present in the three Python replicators?
Complex-type fields dropped from the schema Yes — by design a deliberate skip with a written reason, not a defect
… dropped silently No logged at INFO with the field name and type, always visible
Per-field metadata misaligned by the drop No no per-field metadata vector exists to misalign
Attachment value read on every row No only surviving columns are read

The honest form of the answer is therefore not "the Python is clean and the port is broken", but: the port inherited the skip, kept its reason in a comment, and lost everything that made the skip safe to live with — the log line, the table-level fallback, and a conversion path that never needed column metadata in the first place.

What is not established

  • No replicator was run. Every finding above comes from reading the source. The skip message's presence in a log file, and the absence of any mis-scaling on real data, are unverified at run time.
  • No log file was read. pg_replicator.log, my_replicator.log and ms_replicator.log exist at the repository root and would confirm the skip message at run time; they were not opened. If confirmation is wanted, name one and it can be checked.
  • The project's own fixtures were not opened. Whether Test.accdb, Test2.accdb or TestHarness.accdb contains an Attachment field — and therefore whether the skip path is exercised by the existing tests — would need a DAO run against a fixture, which is a Windows-side action.
  • The Python skip's completeness was not exhaustively audited. This document checks the schema build and the row copy. Other traversals of tdef.Fields (index discovery, key detection) were not swept for a complex-type field.

Recommended action

None for these three replicators. Their handling of DAO type 101 is deliberate, documented in a source comment, and reported to the operator. The defect belongs to the port, and the corrections there — align the metadata vectors, report the skip, decide the complex-type policy openly — are recorded in the port's own investigation, msaccess-replicator-ng/docs/DAO-datatype-bug-2026-10-07.html.
