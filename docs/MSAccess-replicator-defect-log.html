MS Access Replicator Defect Log

Defect Log

Known defects discovered and resolved during development and testing of the MS Access Replicator — covering all three target backends (PostgreSQL, MS SQL Server, MySQL/MariaDB).

Active Defects

No active defects. All known issues have been resolved and committed.

Related Investigations

DAO type 101 (Attachment) and the complex-type skip — investigated 2026-10-07. All three replicators skip Access Attachment (DAO type 101) and multi-valued (102–109) fields when building a table's schema, and each skip is logged at INFO with the field name and its type. A separate investigation asked whether the defect found in the Rust port, msaccess-replicator-ng — where the same skip is silent and leaves the recordset's per-field type and scale metadata misaligned by one position, mis-scaling any Currency or Decimal column after a dropped one — is present here. It is not. The Python readers convert values generically (convert_dao_value_to_python()) with no per-field metadata vector to misalign, and unlike the port they read only the surviving columns, so the attachment's value is never touched. The full comparison is recorded in DAO-datatype-bug-2026-10-07.html.

Resolved Defects (Committed)

Defect Root Cause Observed Behavior Verification Status / Resolution
dbGUID wrapper {guid {...}} not stripped — all three replicators
Affected: PG, MSSQL, MySQL
 DAO returns GUID values wrapped as {guid {xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx}}. None of the three replicators stripped this wrapper before passing the value to the target database. PostgreSQL UUID type and MSSQL UNIQUEIDENTIFIER silently rejected these values, while MySQL CHAR(36) could not fit the 42-character wrapper. PGT01 guid_types: 0 rows inserted (all three rejected). MST01: same — 0 rows. MYT01: INSERT failed with "Data too long". Validation showed Access: 3, target: 0 for all three backends. PGT01 8/8, MST01 8/8, MYT01 8/8 (after all three fixes). guid_types inserts all 3 rows with clean GUID values in all three backends. ✓ Fixed — 2026-08-06 (0f9483c)
convert_dao_value_to_python() in all three src/*.py: strips {guid prefix and trailing } — value = value[6:-1]
Design: Fix applied in convert_dao_value_to_python() — one location for all three replicators, before backend-specific literal conversion.
MySQL GUID braces overflow CHAR(36)
Affected: MySQL only
 After stripping the {guid {...}} wrapper, the GUID still had curly braces — {12345678-ABCD-EF01-2345-6789ABCDEF01} is 38 characters. MySQL CHAR(36) only holds 36 characters. PostgreSQL UUID and MSSQL UNIQUEIDENTIFIER are native types that auto-normalize braces natively — MySQL has no such type. MYT01 guid_types: 2 of 3 INSERTs failed with error 1406 "Data too long for column 'col_guid'". Only rows without braces survived. MYT01 guid_types: 3/3 rows inserted. Validation: Access: 3, MySQL: 3 ✓ ✓ Fixed — 2026-08-06 (0f9483c)
convert_dao_value_to_python() in my_replicator.py: after {guid {...}} strip, also strips plain { } braces from 38-character GUID-like strings — value = value[1:-1]
MySQL TINYINT signed overflow for Access Byte
Affected: MySQL only
 Access DAO type 2 (dbByte) is an unsigned byte (0–255). MySQL type mapping used signed TINYINT (−128 to 127). Values ≥ 128 overflowed. MYT01 integer_types: row "positive typical" (col_byte = 128) failed with error 1264 "Out of range value for column 'col_byte'". Validation: Access: 4, MySQL: 3. MYT01 integer_types: 4/4 rows inserted including col_byte=128. Validation: Access: 4, MySQL: 4 ✓ ✓ Fixed — 2026-08-06 (0f9483c)
type_map in my_replicator.py: type 2 mapping changed from 'TINYINT' to 'TINYINT UNSIGNED'
DAO.Fields errors, PK detection failures, FK creation failures, silent exception swallowing
Affected: PG, MSSQL, MySQL
 Multiple issues in schema discovery and FK creation: (1) DAO.Fields iteration used property access that failed on some field types; (2) primary key detection missed composite keys and certain index-based PKs; (3) foreign key creation failed when the referenced table lacked an explicit unique constraint; (4) several except: pass blocks silently swallowed real errors. Tables with complex field types failed schema discovery. Some tables with valid primary keys were reported as having none. Foreign keys referencing tables without explicit UNIQUE constraints were silently skipped. Legitimate errors in DAO access were invisible. TestHarness.accdb schemas replicate correctly. All 8 tables created with proper types. Foreign keys between related tables are verified. ✓ Fixed — 2026-07-28 (33b72e5)
Commit 33b72e5: "fix: DAO.Fields errors, PK detection, FK creation, and silent exception handling" — applied to all three src/*.py
--create-views combined with --schema caused connection failures
Affected: PG, MSSQL, MySQL
 create_sane_views() assumed DAO and target-database connections were already open, but when called after replicate_schema() the connections had been closed. Also, --create-views was incorrectly placed in a mutually-exclusive argument group, blocking use with --schema. --schema --create-views either refused to run (argparse error) or failed with 'NoneType' object has no attribute 'TableDefs' when views were created after schema. --schema --create-views now works as a single operation: creates schema, then opens fresh connections and creates views. ✓ Fixed — 2026-06-01 (80ebec3, 090b83f)
create_sane_views() now opens its own connections. --create-views removed from mutually exclusive group. Applied to all three replicators.
Foreign key infinite recursion loop when no PK/UNIQUE on referenced table
Affected: PG, MSSQL, MySQL
 create_foreign_key() called ensure_uniqueness_on_base_table() to add a unique constraint on the referenced table. If that function returned None (couldn't create the constraint), the calling code entered an infinite recursive loop trying to re-ensure uniqueness. Replication hung indefinitely when a foreign key referenced a table with no primary key and no suitable columns for a unique constraint. The program appeared frozen with no error message. FKs referencing tables without PKs now log an error and skip — no infinite loop. ✓ Fixed — 2026-06-01 (v1.12/v1.40/v1.2)
create_foreign_key() now checks for None return from ensure_uniqueness_on_base_table(), logs error, and skips. Applied to all three replicators.
sync-deleted batch SQL statement construction error
Affected: PG
 Batch DELETE construction for sync-deleted had incorrect SQL statement assembly — the WHERE (col1, col2) IN ((...), (...)) syntax was malformed for certain key-column configurations. sync-deleted mode failed partway through large batches with SQL syntax errors. Batch deletes across all key-column configurations produce valid SQL. ✓ Fixed — 2026-05-27 (1ec5d46)
Commit 1ec5d46: "correct syn-deleted batch sql statement constrcution"
Pattern: The three most recent defects (dbGUID wrapper, MySQL GUID braces, MySQL TINYINT signed) were all discovered by TestHarness.accdb — an 8-table database covering every Access DAO data type systematically. The GUID defect in particular was a cross-cutting concern: the same {guid {...}} wrapper affected all three backends identically but manifested differently — PG and MSSQL silently rejected the rows, MySQL produced explicit errors. The fix pattern of applying type-conversion fixes in the shared convert_dao_value_to_python() function ensures all three replicators benefit from the same correction.
MySQL-specific risk: MySQL has no native GUID/UUID type that auto-normalizes. The CHAR(36) mapping is a deliberate design choice — it stores the string representation of a GUID. This means any normalization that PG and MSSQL handle natively (braces, case-folding, hyphen placement) must be done in the Python layer for MySQL. The two MySQL-specific fixes above (braces strip, TINYINT UNSIGNED) are examples of MySQL requiring explicit handling where other backends get it "for free" from their type systems.
